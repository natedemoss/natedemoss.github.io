Inference is a memory problem

Nathan DeMoss
November 1, 2026

Abstract

When a language model generates text one token at a time, the GPU spends almost all of its time waiting on memory, not doing arithmetic. This note derives that from a single model of hardware, the roofline, and turns it into one inequality that bounds tokens per second on any chip. Nearly every inference optimization in use today then reads as one of two moves: read fewer bytes per token, or produce more tokens per byte read.

The roofline

Describe a chip by two numbers: peak compute $P$ in FLOP/s, and memory bandwidth $B$ in bytes/s. Describe a workload by its arithmetic intensity $$I = \frac{\text{FLOPs performed}}{\text{bytes moved to and from memory}}.$$ In one second the chip can move at most $B$ bytes, which feeds at most $I B$ FLOPs, and it can never exceed $P$. So the attainable throughput is

$$\text{FLOP/s} \;\le\; \min(P,\; I \cdot B).$$

This is the roofline [1]. Below the ridge point $I^\star = P/B$ a workload is memory-bound: a faster ALU would not help, only fewer bytes or more bandwidth would. Above it, the workload is compute-bound. For an NVIDIA H100 SXM, with $P \approx 989$ TFLOP/s of dense BF16 and $B \approx 3.35$ TB/s of HBM3 bandwidth [2], $$I^\star \approx \frac{989 \times 10^{12}}{3.35 \times 10^{12}} \approx 295 \ \text{FLOP/byte}.$$ A workload has to do about 300 floating-point operations for every byte it reads before the tensor cores become the bottleneck.

Decoding is a matrix–vector product

A transformer with $N$ parameters spends almost all of its forward pass in linear layers. Generating the next token for one sequence pushes a single activation vector through all of them: for each weight matrix $W \in \mathbb{R}^{m \times n}$ it computes $y = Wx$. That is $2mn$ FLOPs (one multiply and one add per weight) against $mn$ weights read. In 16-bit precision each weight is 2 bytes, so

$$I_{\text{decode}} \;\approx\; \frac{2mn}{2mn} \;=\; 1 \ \text{FLOP/byte}.$$

Every weight is fetched from memory, used exactly once, and thrown away. Against a ridge point near 300, decoding at batch size one can use at most about $1/295 \approx 0.3\%$ of the H100's compute. The rest of the chip idles. This is not an implementation problem that a better kernel can fix; it is a property of the workload.

The one formula

If decoding is memory-bound, its speed is set by how many bytes each token forces the chip to read. Per generated token, a model must read all of its weights once, plus the part of its key–value (KV) cache that attention touches. Hence

$$\boxed{\;\text{tokens/s} \;\lesssim\; \frac{B}{\text{bytes}_{\text{weights}} + \text{bytes}_{\text{KV}}}\;}$$

The bound ignores compute entirely, and well-tuned engines get within a modest factor of it at batch one. Take a 7-billion-parameter model in FP16: about 14 GB of weights.

Two things follow immediately. First, the speed ceiling depends on the memory system, not the FLOP count on the box: a chip with half the compute and the same bandwidth decodes just as fast. Second, anything that shrinks the bytes per token raises the ceiling proportionally.

Prefill is the opposite regime

Before generating, the model processes the prompt. All $L$ prompt tokens are known up front, so each weight matrix multiplies an $n \times L$ matrix instead of a vector: $2mnL$ FLOPs for the same $2mn$ bytes of weights, giving $I_{\text{prefill}} \approx L$. A 2048-token prompt has $I \approx 2048$, far past the ridge. Prefill is compute-bound.

This is why the two latencies users notice behave differently. Time to first token scales with prompt length and FLOPs. Time per output token scales with model size in bytes and is nearly flat in everything else. It is also why some serving systems run prefill and decode on separate pools of hardware: they are different workloads that want different chips.

The KV cache

Attention needs the keys and values of every previous token. Per token of context, the cache holds

$$\text{bytes}_{\text{KV}}/\text{token} \;=\; 2 \cdot n_{\text{layers}} \cdot n_{\text{kv-heads}} \cdot d_{\text{head}} \cdot \text{bytes per value},$$

the leading 2 counting keys and values. For a 32-layer model with 32 KV heads of dimension 128 in FP16, that is $2 \cdot 32 \cdot 32 \cdot 128 \cdot 2 = 512$ KiB per token. At a 4096-token context, one sequence's cache is about 2.1 GB, and generating each new token reads all of it.

Unlike the weights, the KV cache is not shared across sequences. Batching amortizes weight reads over the batch, but each sequence still reads its own cache, so the attention part of decoding keeps an intensity near 1 no matter how large the batch. At long contexts and large batches, KV reads overtake weight reads and become the term that matters in the boxed formula.

Grouped-query attention (GQA) and multi-query attention attack exactly this term: several query heads share one key–value head [3]. With 8 KV heads instead of 32, the cache above drops to 128 KiB per token, a 4× reduction in the bytes attention reads, and each KV value is reused by 4 query heads, which raises attention's intensity by the same factor.

Every optimization, in one table

With the formula in hand, the standard toolbox sorts itself into two columns.

Batching is the most direct. A step that decodes $b$ sequences reads the weights once and does $b$ times the work, so the weight part of the workload has $I \approx b$. Up to roughly $b \approx I^\star$, a batched step costs about the same wall time as a single one, which is why servers batch aggressively and why per-token cost falls so steeply with load. The catch is the KV cache, which grows with $b$ and does not amortize.

Quantization works for decode for a reason that has little to do with arithmetic. In weight-only schemes, low-precision weights are dequantized in registers and the math still runs in 16 bits. The win is purely that a 4-bit weight is a quarter of the bytes. The table above shows the ceiling rising accordingly.

Mixture of experts is a bandwidth trick at small batch: each token is routed through only a few experts, so it reads only their weights. Mixtral 8×7B has about 47B parameters but uses about 13B per token [4]. At large batch, different tokens pick different experts, most experts get read every step, and the advantage over a dense model shrinks.

Speculative decoding exploits the gap between $I = 1$ and $I^\star \approx 300$ directly. A cheap draft model guesses several tokens; the large model checks all of them in one forward pass. Checking $k$ tokens is a matrix–matrix product with $I \approx k$, and while $k \ll I^\star$ it costs about the same as producing one token. The idle compute becomes speed. Remarkably, a rejection-sampling acceptance rule makes this exact: the output distribution is unchanged [5].

Where the model breaks

The roofline is a bound, not a prediction, and the boxed formula holds only while its assumptions do.

  • Large batches. Once the weight intensity $b$ passes $I^\star$, the step becomes compute-bound and the levers change: FLOPs, not bytes, are what to cut.
  • Small models and overheads. For tiny models, kernel launch latency, synchronization and the host side can dominate, and the real number falls well below the bandwidth line.
  • Caches. If the weights fit in on-chip cache (small models on CPUs, or some accelerators with large SRAM), the relevant $B$ is the cache bandwidth, not DRAM.
  • Achieved bandwidth. Real kernels reach a large fraction of peak bandwidth, not all of it, so practical numbers sit somewhat below the table.

Within those limits, one inequality explains why a laptop runs a 4-bit 7B model at a usable speed, why serving gets cheaper with more users, why attention variants are judged by their cache size, and why spending FLOPs to save bytes is so often the right trade.
